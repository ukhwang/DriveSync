# [2026 현대자동차그룹 차량용 앱 개발 공모전] 서비스 기획서 (최종본)

## 0. 서비스 개요

- 서비스명: DriveSync (드라이브싱크): B2B 외근 영업직을 위한 차량 기반 고객 방문 워크플로 엔진
- 핵심 정의: "운전 중 떠오른 생각을, 도착 후 실행 가능한 업무로."

DriveSync는 내비게이션 목적지와 잔여 시간(ETA), 차량의 주행·정차 상태를 인식하는 Pleos 기반 B2B 업무 앱입니다. 고객 방문 하나를 아래 다섯 단계로 이어지는 하나의 세션으로 관리하고, 그 결과를 고객별 방문 이력으로 쌓습니다.

> 방문 전 브리핑 → 이동 중 음성 브리핑·단발성 메모 → 도착 후 미팅 치트시트 → 미팅 후 디브리핑 → 승인형 후속 실행

**문제 가설**
하루 2~5곳의 거래처를 차로 도는 외근 영업직은 출발 직전과 방문 직후에 미팅 전략과 후속 조치를 가장 많이 떠올립니다. 그러나 주행 중에는 안전상 기록하기 어렵고, 사무실에 돌아오면 기억이 흐려집니다. 그 결과 CRM 입력이 늦어지고 후속 연락이 빠진다는 가설에서 출발합니다.

※ 이 가설은 제출 시점에는 아직 검증되지 않았습니다. 차로 거래처를 도는 현직자 5명 이상(제약·의료기기 영업, 보험 설계사, B2B 솔루션 영업 등)에게 예비 인터뷰를 진행할 예정입니다. 확인할 항목은 네 가지입니다.
1. 하루 방문 수
2. 방문 후 기록 시점과 방식
3. 후속 연락 누락 경험
4. 비용 지불 주체

**핵심 가치: DriveSync를 정의하는 세 가지**
1. ETA-aware Session: 목적지까지 남은 시간에 맞춰 브리핑 분량과 시점을 자동으로 조절합니다.
2. Driving/Parking Context Switch: 플랫폼의 UX 제한 상태에 따라 주행 중에는 최소 모드로, 정차 후에는 작업 모드로 전환합니다.
3. Conversation-to-Action: 메모와 디브리핑이 요약으로 끝나지 않습니다. 사용자가 검토·승인하면 실제로 실행되는 업무가 됩니다.

## 1. 차량 특화성

"스마트폰과 모바일 CRM이 있는데, 왜 차에 DriveSync가 필요한가?"

스마트폰은 사용자가 지금 어디로 가는지, 몇 분 뒤 도착하는지, 지금 화면을 봐도 되는 상태인지 알지 못합니다. DriveSync는 두 가지 차량 정보를 방문 세션에 직접 연결합니다.
- 내비게이션 목적지와 ETA (NaviHelper)
- 플랫폼의 주행 UX 제한 상태 (CarUxRestrictions)

그래서 출발·주행·도착·재출발이라는 전환 시점마다 그 순간에 허용되는 업무만 보여줍니다. 이동시간은 안전하게 '듣기'에 쓰고, 정차 시간은 대화면에서 '확인·승인'에 씁니다.

### ① 주행 안전 우선 설계
- 단일 판단 기준: 화면과 입력을 어디까지 허용할지는 CarUxRestrictions 상태 하나로 결정합니다. 기어가 P단이라는 이유만으로 모든 조작을 허용하지 않습니다.
- 주행 제한 상태: 화면에는 목적지, ETA, 세션 상태, 메모 버튼만 보입니다. AI의 질문·반론·양방향 대화, 텍스트 입력, 목록 탐색은 막습니다.
- Fail-Safe: 차량 상태를 믿을 수 없을 때(수신 실패, 권한 거부 등)는 주행 제한 상태로 간주합니다.
- 운전자 우선권: 음성 출력은 탭 한 번으로 즉시 멈춥니다. 내비 안내음이 나오면 오디오 포커스를 양보하고 일시정지합니다.
- 표현 원칙: 실차 검증 전까지 '사고 위험 감소'라고 주장하지 않습니다. '플랫폼 주행 제한 정책 준수'라고만 씁니다.

### ② ETA 맞춤 음성 브리핑 (ETA-Aware Session)
출발 전 정차 중에는 화면으로, 주행 중에는 일방향 음성(TTS)으로 브리핑합니다. 주행 중 음성은 운전자의 응답을 요구하지 않습니다. 남은 이동시간이 길수록 미팅 전 준비할 여유가 많으므로 길게, 짧을수록 핵심만 전달합니다.

| ETA | 출발 전 화면 | 주행 중 음성 브리핑 | 도착 5분 전 |
|---|---|---|---|
| 10분 미만 | 핵심 3줄 카드 | 30초 이내: 오늘 목표 + 꼭 확인할 질문 1개 | 생략 |
| 10~25분 | 핵심 3줄 + 우려사항 | 약 1분: 지난 방문 결과·우려사항·질문 3개 | 15초 재요약 |
| 25분 이상 | 상세 브리핑 카드 | 약 2분 브리핑 후 무음 유지 | 15초 재요약 |

- 주행 중 ETA가 크게 바뀌면 남은 분량을 다시 계산합니다. 시간이 모자라면 핵심 문장만 재생합니다.
- 브리핑은 라디오처럼 듣기만 하면 됩니다. 운전자에게 질문하거나 답을 요구하지 않습니다.
- TTS 권한이 없으면 정차 중 화면 브리핑으로 대신합니다.

### ③ 단발성 음성 메모 (One-Shot Voice Capture)
- 시작: 주행 모드 화면의 큰 버튼 하나를 한 번 탭합니다. Gleo 음성 호출로 시작하는 기능은 P1입니다.
- 동작: 한 번 말하면 SpeechToText로 텍스트로 바꿔 저장하고 확인음만 냅니다. 말이 끝나면(약 3초 무음) 자동 저장되며 최대 길이는 2분입니다(설정으로 변경 가능). AI 응답이나 꼬리질문은 없습니다.
- 적용 조건: 공모전 환경의 STT 권한과 주행 중 DO(Distraction Optimization) 허용 범위를 확인한 뒤 적용합니다. 허용되지 않으면 버튼을 숨기고 정차 중 입력으로 대신합니다.

### ④ 고객 방문 단위 5단계 업무 루프

| 단계 | 차량·UX 상태 | 사용자 경험 및 시스템 동작 |
|---|---|---|
| 1. 방문 전 (출발 전) | 정차 / 제한 해제 | 내비 목적지와 방문 일정을 맞춰보고, 사용자가 확인하면 세션 시작. ETA에 맞춘 브리핑 카드 확인 |
| 2. 이동 중 | 주행 / 제한 활성 | ETA 맞춤 음성 브리핑. 운전자가 원하면 단발성 음성 메모 (대화 없음) |
| 3. 도착 후 (미팅 직전) | 제한 해제 + P단 확인 | 대화면에 치트시트 공개: 핵심 3줄, 우려사항, 예상 질문, 이동 중 메모 |
| 4. 미팅 후 (차량 복귀) | 정차 / 제한 해제 | 텍스트나 음성으로 디브리핑 → 서버를 거친 LLM이 결정사항·약속·후속 업무를 뽑아냄 |
| 5. 다음 이동 전 | 정차 / 제한 해제 | 후속 작업을 하나씩 검토·승인 후 실행. 못 끝낸 작업은 다음 방문 브리핑으로 넘어감 |

## 2. 창의성

DriveSync는 '차에 탑재한 또 하나의 음성 AI 비서'가 아닙니다. 고객별 방문 이력과 후속 작업 상태를 쌓아가는 영업 워크플로 엔진입니다.

### ① "Gleo에게 같은 말을 시키면 되지 않나?"에 대한 답
- 상태: 범용 AI는 요청이 있어야 답합니다. DriveSync는 출발·주행·도착·재출발이라는 차량 이벤트에 따라 5단계 세션을 스스로 진행합니다. 사용자가 매번 상황을 설명하거나 프롬프트를 쓸 필요가 없습니다.
- 데이터: 한 고객사에 대한 1차·2차·N차 방문 기록, 우려사항의 변화, 못 끝낸 후속 작업을 구조화된 DB에 남깁니다. 이 내용은 다음 방문 브리핑에 자동으로 넘어가므로, 쓸수록 브리핑이 정확해집니다.
- 실행 책임: AI 결과를 바로 실행하지 않습니다. 6단계 승인 상태와 실패 기록으로 업무가 끝날 때까지 추적합니다.

Gleo와는 경쟁이 아니라 보완 관계입니다. Gleo는 차량 전체의 음성 인터페이스를 맡고, DriveSync는 영업 업무의 세션·데이터·실행 상태를 맡습니다. Gleo Interface(App Schema) 심사를 통과하면 "메모 남겨줘", "다음 방문 브리핑 들려줘" 같은 음성 호출의 입구로 Gleo를 씁니다.

### ② 대안 서비스 대비 차별성

| 비교 대상 | 한계 | DriveSync의 차이 |
|---|---|---|
| 범용 대화형 AI | 매번 맥락 설명·프롬프트 필요, 주행 제한 상태를 모름 | 차량 이벤트로 세션 자동 진행, 고객별 이력 자동 주입 |
| 모바일 CRM | 작은 화면에서 여러 필드를 직접 입력 | 정차 전환 시점에 대화면에서 확인·승인만 |
| 휴대폰 지오펜스 앱 | 도착은 알지만 ETA와 주행 제한 상태를 모름 | ETA 맞춤 브리핑, 제한 상태별 화면 전환 |

### ③ 6단계 승인형 실행 (Human-in-the-Loop)

| 상태 | 의미 | 외부 반영 |
|---|---|---|
| Draft | AI가 만든 초안 | 없음 |
| Review | 정차 중 사용자가 확인·수정 | 없음 |
| Approved | 사용자가 하나씩 승인 | 실행 대기 |
| Executed | 외부 시스템에 반영 완료 (결과 로그 저장) | 반영됨 |
| Failed | 실행 실패, 원인 표시 | 없음 |
| Retry | 다음 정차 때 재시도 안내 | 다시 승인 후 실행 |

실패한 작업을 성공으로 표시하지 않습니다. 같은 작업이 두 번 실행되지 않도록 실행 키(idempotency key)로 막습니다.

## 3. 기술 활용성

Pleos 공식 문서의 SDK 호환성 기준을 따릅니다. 모든 차량 기능은 실행 중에 지원 여부를 먼저 확인하고, 지원되지 않으면 미리 정해둔 대체 동작으로 전환합니다. 에뮬레이터의 가상 차량 데이터를 실제 측정값처럼 표현하지 않습니다.

### ① SDK·API 연동 전략

| 기능 | API / SDK | 공식 문서 기준 | 활용 및 대체 동작 |
|---|---|---|---|
| 주행 안전 제어 | AAOS CarUxRestrictions | 표준 API | 화면·입력 허용 범위를 정하는 유일한 기준 (P0) |
| 차량 상태 | Pleos Vehicle SDK / AAOS CarPropertyManager | 차종별로 다름, capability 확인 API 제공 | 기어·속도를 세션 전환의 보조 신호로 사용. 미지원 시 CarUxRestrictions만으로 동작 |
| 목적지·ETA | Pleos NaviHelper SDK | 내비 탑재 차량에서 호환 | 목적지·경로 정보로 방문 일정 매칭, ETA로 브리핑 분량 조절. 에뮬레이터 제약 구간은 Mock임을 명시 |
| 음성 입출력 | Pleos SpeechToText / TextToSpeech | 문서상 전 차종 호환 | 단발성 메모와 음성 브리핑. 공모전 환경 권한 확인 후 적용, 실패 시 정차 중 텍스트·화면 브리핑 |
| 위치 | Pleos FusedLocation SDK | 차종별로 다름, isSupported로 확인 | 방문지 도착 보조 태깅. 미지원 시 NaviHelper 목적지 기준 |
| AI 구조화 | 전용 백엔드 프록시 + 외부 LLM | 서버 경유 호출로 확정 | API 키는 APK에 넣지 않고 서버에만 보관 |
| 음성 호출 확장 | Gleo Interface (App Schema) | 심사·승인 필요 | P1. 승인 후 메모·브리핑 호출 함수 연동 |

### ② 핵심 데이터 모델 (엔터티 6개)

| 엔터티 | 주요 필드 | 역할 |
|---|---|---|
| Customer | 고객 ID, 업체명, 담당자, 누적 이력 요약 | 고객사 기본 정보와 여러 차례 방문의 맥락 |
| Visit | 고객 ID, 방문 목적, 예정 시각, 장소 좌표 | 일정·목적지 매칭으로 생기는 방문 단위 |
| Session | 방문 ID, 시작·종료 시각, ETA 구간, 현재 상태 | 이동과 미팅을 아우르는 상태 머신 |
| Note | 텍스트, 입력 시점, 입력 방식(음성/텍스트), 단계 | 이동 중 메모와 디브리핑 원본 기록 |
| Insight | 핵심 3줄, 우려사항, 예상 질문, 항목별 출처(사용자 입력/AI 추론) | JSON Schema로 검증한 치트시트 |
| Action | 유형, 초안, 6단계 상태, 실행 키, 결과 로그 | 승인형 후속 작업 |

Insight는 항목마다 '사용자가 말한 것'과 'AI가 추론한 것'을 나눠 표시합니다. 그래서 사용자는 미팅 전에 어떤 내용을 직접 확인해야 하는지 알 수 있습니다.

### ③ 시스템 아키텍처

차량 앱 (Kotlin, ViewModel + StateFlow, Coroutine):
1. Vehicle Context Adapter: CarUxRestrictions, Vehicle SDK, NaviHelper, FusedLocation 이벤트를 하나의 차량 맥락으로 정리합니다. 실제(Real) 구현과 모의(Mock) 구현을 같은 인터페이스로 분리합니다.
2. Safety & Policy Controller: 제한 상태별로 허용할 기능을 정하고, Fail-Safe 차단과 음성 출력 중단·복구를 처리합니다.
3. Session & Visit Engine: 방문 일정과 이동 세션을 묶고, ETA로 브리핑 분량을 계산하며, 중단된 세션을 복구합니다.
4. AI Gateway: LLM은 백엔드를 통해서만 호출하고, 응답이 스키마에 맞는지 검증합니다.
5. Action Engine: 6단계 상태 전환과 실행·실패·재시도를 처리합니다.
6. Local Store: Room + SQLCipher로 암호화 저장하고, 오프라인에서도 세션을 보존합니다.

백엔드 (경량):
- 인증된 요청만 받는 LLM 프록시: 입력 검증, 사용량 제한, JSON Schema 검증
- 승인된 후속 이메일을 발송 API로 실제 발송
- 팀 단위 방문 이력 동기화는 P1

### ④ 세션 상태 머신

| 상태 | 진입 조건 | 다음 상태 |
|---|---|---|
| IDLE | 앱 실행, 진행 중인 세션 없음 | 방문 선택 → PREPARE_SESSION |
| PREPARE_SESSION | 정차 + 방문·목적지 매칭 확인 | 주행 제한 활성 → DRIVING_LIMITED |
| DRIVING_LIMITED | 주행 제한 활성 | 상태 불확실 → PAUSED_BY_POLICY / ETA 5분 이하 → ARRIVAL_PENDING |
| PAUSED_BY_POLICY | 차량 상태 수신 실패, 권한 거부 | 상태 복구 → 이전 상태 |
| ARRIVAL_PENDING | 도착 임박 | 제한 해제 + P단 → PARKED_REVIEW |
| PARKED_REVIEW | 제한 해제 확인 | 디브리핑 완료 → AWAITING_APPROVAL |
| AWAITING_APPROVAL | 후속 작업 초안 생성 | 승인 → EXECUTING / 주행 시작 → 승인 보류 |
| EXECUTING | 하나씩 승인된 작업 실행 | 모두 처리 → COMPLETED / 실패 → Retry 표시 |
| COMPLETED | 세션 종료 | 다음 방문 → PREPARE_SESSION |
| ERROR | 복구할 수 없는 오류 | 로컬 저장본으로 세션 복구 |

예외 처리:
- 네트워크 단절: 입력을 로컬에 저장하고 대기합니다.
- 중복 차량 이벤트: 디바운스로 걸러냅니다.
- 앱 백그라운드 전환: 로컬 데이터로 복구합니다.
- ETA 급변: 브리핑 분량을 다시 계산합니다.
- 음성 재생 중 새 응답 도착: 겹쳐 재생하지 않고 대기열에 넣습니다.

### ⑤ MVP 개발 우선순위

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| P0-1 | Pleos Connect 에뮬레이터에서 Kotlin APK 구동 | 핵심 화면 3개 렌더링 |
| P0-2 | 주행 안전 상태 머신 | 제한 상태에서 금지 기능 접근 0건 |
| P0-3 | 방문 세션 + NaviHelper + ETA 브리핑 조절 | ETA 구간별 브리핑 분량 전환 |
| P0-4 | 백엔드 LLM으로 치트시트·후속 작업 생성 | 스키마 검증을 통과한 결과만 표시 |
| P0-5 | 6단계 승인형 실행 1종 실제 작동 | 미승인 실행 0건, Failed → Retry 동작 |
| P0-6 | 단발성 음성 메모·음성 브리핑 (STT/TTS) | 권한 확인 시 에뮬레이터에서 동작, 권한 없으면 대체 경로 동작 |
| P1 | Gleo Interface, 팀 동기화, 캘린더 연동 | 심사·권한 확보 후 |
| P2 | CRM 연동, 관리자 대시보드 | 파일럿 검증 후 |

**본선 라이브 시연 액션**
1. 미팅 디브리핑에서 나온 고객 후속 이메일을 Draft → Review → Approved → Executed 순서로 넘깁니다.
2. 발송은 차량 앱이 아니라 백엔드 발송 API가 맡아 실제 수신함으로 보냅니다. 성공·실패 표시는 서버 응답만 근거로 합니다.
3. 네트워크를 끊은 상태에서 Failed → Retry 흐름을 보여줍니다.
4. 방문 리포트가 암호화되어 저장되는 것도 함께 보여줍니다.
5. 시뮬레이션 데이터가 쓰인 화면에는 '시뮬레이션' 배지를 붙입니다.

### ⑥ 개인정보 및 영업 데이터 보호
- 방문 업무에 필요한 항목만 수집하고, 그 목적으로만 씁니다.
- 로컬의 민감 정보는 SQLCipher로 암호화하고, 서버 토큰은 Android Keystore에 보관합니다.
- 고객 정보를 외부 LLM에 보내기 전에 사용자의 명시적 동의를 받습니다. 서버는 요청을 처리한 뒤 원문을 보관하지 않는 것을 원칙으로 합니다.
- 사용자는 고객 단위나 방문 단위로 기록을 지울 수 있습니다.
- 음성 원본과 전사 데이터의 보존 기간은 사용하는 SDK의 데이터 처리 조건을 확인한 뒤 정합니다.

## 4. 사업성

검증되지 않은 MAU나 매출을 가정하지 않습니다. 아래 수치는 모두 검증할 가설입니다.

### ① 시장 현실과 단일 주력 BM: B2B 영업 조직 라이선스
Pleos Connect는 2026년 5월 신형 그랜저에 처음 적용됐고, 현대자동차그룹은 2030년까지 약 2,000만 대 이상으로 적용을 넓힐 계획입니다. 초기 1~2년은 탑재 차량이 적습니다. 그래서 불특정 운전자 대상 B2C 구독보다, 차로 이동하는 것이 업무의 일부인 영업 조직을 단일 주력 고객으로 잡습니다. 제약, 의료기기, 보험, 기업 솔루션 영업이 여기에 해당합니다.
- 비용은 회사가 냅니다. 방문 기록 누락과 후속 연락 지연은 영업 성과와 바로 연결됩니다. 그래서 개인보다 영업 조직의 지불 의향이 높다고 가정합니다.
- 가격 가설: 좌석당 월 1만~1.5만 원입니다. 파일럿 단계에서는 소규모 영업팀에 무료로 제공해 도입 문턱을 낮춥니다.
- 고객을 붙잡는 힘(Lock-in): 기능보다 쌓여가는 고객별 방문 이력이 핵심 경쟁력입니다. 오래 쓸수록 브리핑 품질이 올라가고, 그 이력이 조직의 영업 자산이 됩니다.

### ② 원가 구조 가설

| 항목 | 가정 | 월 환산 (영업사원 1인) |
|---|---|---|
| 방문 수 | 하루 3건 × 20일 | 월 60건 |
| LLM 호출 | 방문당 3회(브리핑, 치트시트, 디브리핑 추출), 총 약 1만 토큰 | 월 약 60만 토큰 → 경량·중형 모델 기준 수백~수천 원 |
| STT/TTS | Pleos SDK 사용 | 별도 과금 여부 확인 필요 |
| 서버 | 경량 프록시·DB | 초기에는 소규모 고정비 |

가격 가설에 비해 변동 원가가 낮아 마진 구조는 성립할 것으로 보입니다. 다만 모델 단가와 실제 토큰 사용량은 파일럿에서 측정해 확정합니다. 무료 구간에는 월 세션 수 상한을 둡니다.

### ③ 유통과 확장
- 유통: Pleos App Market을 통해 차량에 배포합니다. 법인 차량에 일괄 배포하고 관리하는 방식은 플랫폼 정책을 확인한 뒤 설계합니다.
- 확장: Pleos 탑재 차량이 없는 팀원을 위해, 같은 방문 데이터를 쓰는 모바일 보조 앱을 둡니다. 차량 경험은 탑재 차량에서만 제공합니다. 이후 사내 CRM 연동과 관리자 대시보드로 팀 단위 가치를 키웁니다.

### ④ 초기 검증 목표 (가설 기반 핵심 지표)

| 측정 지표 | 목표 (가설) | 검증 방식 |
|---|---|---|
| 방문 후 기록 완료 시간 | 기존 방식 대비 30% 이상 감소 | 같은 시나리오로 소요 시간 비교 |
| 후속 작업 추출 정확도 | 사용자 확인 기준 90% 이상 | 생성된 Insight·Action의 수정률 |
| 승인 없이 실행된 작업 | 0건 | 상태 머신 무결성 테스트 |
| 주행 제한 상태 기능 위반 | 0건 | 제한 시나리오 자동·수동 검증 |
| 파일럿 2주차 주간 재사용률 | 50% 이상 | 실제 방문 세션 기록 빈도 |
| 유료 의향 | 파일럿 팀 중 1곳 이상 도입 의향서(LOI) | 파일럿 종료 후 구매 담당자 인터뷰 |

### ⑤ 검증 절차
1. 예비 인터뷰 (1차 결과 발표 전, ~11/23): 제약·의료기기 영업, 보험 설계사, B2B 솔루션 영업 현직자 5명 이상에게 방문 전후 기록 방식, 후속 연락 누락 경험, 비용 지불 주체를 확인합니다. 결과에 따라 타깃 직군과 핵심 기능 우선순위를 조정합니다.
2. 본선 전 시나리오 테스트: 5~10명에게 에뮬레이터 시연을 보여주고 기록 시간과 추출 정확도를 측정합니다.
3. 2주 파일럿: 실제 방문에서 재사용률과 원가를 측정합니다.
4. 지불 의향 확인: 영업 조직의 구매 담당자와 가격 가설을 검증하고 도입 의향서(LOI)를 받습니다.
